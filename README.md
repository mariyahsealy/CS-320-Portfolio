# CS-320-Portfolio
This repository holds two parts of my work from this course. From Project One, I included my contact service (Contact.java, ContactService.java, ContactTest.java, and ContactServiceTest.java). From Project Two, I included my summary and reflections report, where I explained the testing techniques I used and why. The contact service is a small program that keeps contacts in memory, with no database. Each contact has an ID that can never change, a first and last name, a phone number that has to be exactly 10 digits, and an address. The service can add, delete, and update contacts. I wrote 60 JUnit tests to check that it follows every rule in the customer's requirements, and when I measured them with a coverage tool called JaCoCo, they reached 100% line, instruction, and branch coverage.

Working on these projects changed how I think about making sure software actually works. At first I thought a test was done once I had written it and it looked right. My feedback showed me otherwise: some of my tests checked a string that wasn't actually over the limit, and a couple were missing their @Test label, so they never ran at all. Now I compile and run every test each time and measure coverage with a tool instead of guessing. I also test the edges of every rule, like the exact limit, one past it, and null, because that is where mistakes tend to hide. As for security, the work here was really about protecting the data. Every field is checked in one place, the setter, and the constructor uses those same setters, so bad data can't sneak in another way. I also made the contact ID impossible to change and wrote a test to prove it. That is basic input validation, not a full security review, but the habit is one I plan to keep: never trust input, and check it in one consistent place.

Understanding what the customer needs started with breaking the requirements into small rules I could check. A sentence like "the phone must be exactly 10 digits" turned into three tests: 9 digits is rejected, 10 digits is accepted, and 11 digits is rejected. I named every test after the rule it checks, so anyone can open the test file and see whether each requirement is covered. I also learned that a program can pass every test and still be wrong if I misread what the customer wanted, so when something is unclear I would rather ask than guess. That is why I wrote about acceptance testing in my reflections report, since it is the step where the customer confirms the software really meets their needs.

When I design software, I try to keep each rule in exactly one place and keep each piece small. In the contact service, validation lives in the setters, one helper method handles the "contact not found" case for every update, and a HashMap keyed by ID keeps things simple and fast. That also made the code easier to test, because there was only one place to check for each rule. I found that design and testing shape each other: when something was hard to test, it usually meant the design needed to be simpler. Going forward, I want to write the test for a requirement at the same time as the code instead of afterward, so mistakes show up while they are still easy to fix.
